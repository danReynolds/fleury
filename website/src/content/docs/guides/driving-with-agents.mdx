A Fleury app already describes its controls as roles, labels, values, and
actions. `fleury_mcp` gives an AI agent that semantic view of the app and lets
it use the actions the controls advertise. It does not scrape terminal cells or
guess which keys might work.

You do not add MCP code to the application. Start with ordinary Fleury widgets,
then connect an MCP host to the same `runApp` entry point you use in a terminal.

## Work on the app in your terminal

For development, let the agent attach to the native app you are already using:

```sh
fleury run --agent bin/run_app.dart
```

Configure your MCP host to start `dart run fleury_mcp --attach` from the app's
project directory. Add the development dependency described below first. If the
host runs elsewhere, `dart run` can't find the server: use a globally activated
`fleury_mcp --attach` (described below) with `--project=/absolute/app/path`. If
several sessions are running, the attachment error lists their IDs for
`--session=<id>`.

The agent reads `get_inspection` for rendered cells, styles and semantics from
one frame boundary. Passing a semantic `node` also returns widget ancestry,
layout constraints, size, bounds and clipping. It can enter a draft with
`set_value`, edit source, and check `get_dev_status` for the next completed
reload before inspecting the result. A normal hot reload preserves existing
widget state. Compiler errors appear in the reload report while the old app
keeps running. `reload_app` triggers that loop explicitly; `restart_app` resets
state and returns a fresh inspection.

Every action in an attached session requires the `targetRef` returned by the
latest inspection, including controls with stable IDs. Restart invalidates all
old references. Disconnecting MCP leaves the native app and its draft running.

This attachment supports macOS/Linux source sessions with an interactive
terminal and hot reload. The supervisor exposes an opted-in, authenticated
loopback endpoint for development. Resize the actual terminal; raw keyboard and
pointer injection are not exposed in this first version. Cell inspection
reports logical paint, including wide-character roles, rather than an emulator
screenshot or image pixels. Its default region is capped to 200 by 100 cells;
pass `region` with `left`, `top`, `cols` and `rows` to inspect another area.

There is no `fleury_mcp` import and no manually assembled agent protocol. The
controls already publish the useful contract:

| Visible control | Semantic contract | Agent operation |
|---|---|---|
| Release version | `textField`, current text, `setValue` | `set_value` |
| Tests passed | `checkbox`, checked state, `setValue` | `set_value` |
| Prepare release | `button`, `activate` | `invoke_action` |
| Status text | `text`, current label | read after the action |

No extra identity or agent wrapper is needed for this read-and-act workflow.
The server returns the current target for each control and refuses detectable
stale positional references.

## Spawn an app for an MCP host

The MCP server is a separate executable so your application has no agent
dependency. It connects to the app over a Unix-domain socket, so it runs on
macOS and Linux. Add it as a development dependency of the app it will drive:

```yaml
dev_dependencies:
  fleury_mcp: ^0.1.0
```

Run `dart pub get`. The server exact-pins its matching Fleury version, so pub
resolves a compatible framework for both the server and app. From the application
directory, start it with the command that runs your app after `--`:

```sh
dart run fleury_mcp -- dart run bin/run_app.dart
```

<details>
<summary>Before publication or when using a Fleury checkout</summary>

Activate the executable from the same checkout as the app. From that checkout's
root, bootstrap once and activate:

```sh
dart tool/fleury_dev.dart bootstrap
dart pub global activate --source path packages/fleury_mcp
```

From `packages/samples`, this runs the example above:

```sh
fleury_mcp -- dart run bin/samples.dart agent-guide
```

For your application, use `fleury_mcp -- dart run bin/run_app.dart`. Use the
installed `fleury_mcp` command in host configuration instead of
`dart run fleury_mcp`, and reactivate it whenever the checkout's Fleury changes.
</details>

An MCP host that uses JSON configuration can express the same command as:

```json
{
  "mcpServers": {
    "release-app": {
      "command": "dart",
      "args": ["run", "fleury_mcp", "--", "dart", "run", "bin/run_app.dart"]
    }
  }
}
```

Hosts that add servers from their own command line take the same command. With
Claude Code, for example:

```sh
claude mcp add release-app -- dart run fleury_mcp -- dart run bin/run_app.dart
```

`fleury_mcp` starts the app itself. The app runs in remote mode, sends its
semantic tree over a private local socket, and receives semantic actions back.
Its terminal rendering is not part of the agent connection. The app gets an
80 × 24 viewport; pass `--cols=<n>` and `--rows=<n>` before the `--` to change
it, or use the `resize` tool during a session.

Configure the host to start the server from the application package. Both
`dart run fleury_mcp` and the app's relative entrypoint need that directory.
If the host cannot set it, globally activate the matching server release with
`dart pub global activate fleury_mcp 0.1.1`, use the installed `fleury_mcp`
command, and give it the app entrypoint's absolute path.

Desktop hosts often start servers with a minimal `PATH`. Give the host the
absolute path to Dart (`which dart` prints it) and include the Dart SDK's `bin`
directory in the server's `PATH`, since the app command also invokes `dart`.
For a globally activated server, use the absolute path printed by
`which fleury_mcp` instead.

`dart run` compiles the app each time the server starts, and `fleury_mcp`
suggests compiling it once instead: `dart compile exe bin/run_app.dart -o my_app`,
then `dart run fleury_mcp -- ./my_app`. A compiled app starts faster, but its debug
tooling is off, so `read_frames`, `read_logs`, and `read_errors` return
`available: false` unless the app passes `DebugConfig(enabled: true)` to
`runApp` (see [Inspect what happened](#inspect-what-happened)).

The server supports [the stateless MCP `2026-07-28`
revision](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
and the `2025-06-18` initialization flow for existing hosts. The driving
workflow below is the same on both.

## Give the agent one outcome

Once the host is connected, ask for a user-visible result instead of naming
protocol tools:

> Set the release version to 1.0.0, mark the tests as passed, prepare the
> release, and tell me the final status.

A host can complete that request in four semantic steps:

1. Read the UI with `get_ui`, or narrow a large screen with `find_nodes`.
2. Find **Release version** and use `set_value`. Select **Tests passed** from
   the settled `ui` returned by that action.
3. Set **Tests passed**, then select and activate **Prepare release** from the
   next returned `ui`.
4. Report **Ready to publish 1.0.0** from the final returned `ui`.

The agent uses ids returned by `get_ui` or `find_nodes`; application authors do
not hard-code those ids into prompts. The server validates values against each
control's semantic schema before dispatching them.

## Choose logical actions before keys

Use the action a control advertises whenever one exists:

- `set_value` changes a field, checkbox, switch, select, slider, or other
  settable control in one operation.
- `invoke_action` activates buttons and invokes domain actions such as select,
  open, close, submit, increment, or cancel.

The current `2026-07-28` surface deliberately exposes only actions whose target
travels in the request. Legacy `2025-06-18` clients also have `press_key` for
keyboard routing and shortcuts, and `type_text`, which types text into the
focused field. Those focus-relative tools stay off the stateless surface until
Fleury can carry an explicit target or focus lease with them.

This is the same distinction used in [Testing](/fleury/guides/testing/): test or
drive application behavior through semantics, then cover keyboard and pointer
routing separately when those physical paths matter.

## Use the UI returned by each action

Every mutating MCP tool returns the settled UI, which counts as a fresh read.
Select the next control from that result instead of retaining a target from an
earlier tree. Use `find_nodes` when the full tree is capped or you want a
narrower view.

Built-in controls currently receive positional semantic ids. They are safe for
an immediate read-and-act sequence, and Fleury returns `stale_reference` rather
than dispatching when a positional target is no longer current. Controls that
represent durable records, such as rows an agent may come back to, still need
distinct keys or stable semantic ids.

<details>
<summary>How positional targets are checked</summary>

A positional node includes `stableId: false` and an opaque `targetRef`. A
`2026-07-28` client echoes both the node id and that reference when it acts,
taking the current `targetRef` from the latest returned UI. Fleury rejects the
call if the slot now contains a control with a different observable identity
token. A semantically identical unkeyed replacement is intentionally
indistinguishable. The reference is protocol bookkeeping, not an application id
to copy into code or prompts.

</details>

An explicit `Semantics(id: ...)` gives a custom semantic control a durable id.
Built-in controls don't accept an id yet. Don't wrap one in `Semantics` just to
add an id: that duplicates the semantics the control already publishes.

## Describe custom controls

Built-in controls already expose their semantics. A custom interactive widget
must say what it is, what it is called, and which actions it supports:

```dart
Semantics(
  id: const SemanticNodeId('retry-upload'),
  role: SemanticRole.button,
  label: 'Retry upload',
  actions: const {SemanticAction.activate},
  onAction: (action) {
    if (action == SemanticAction.activate) retryUpload();
  },
  child: const Text('[ Retry ]'),
)
```

Prefer a first-party control when its behavior fits. Besides helping agents,
the same semantic contract powers Fleury tests and the browser accessibility
surface.

## React to changing screens

After an action, use its returned `ui` before choosing the next target. For
changes the app makes on its own, use `wait_for_change` instead of polling. A
client passes the `uiRevision` from its last UI result as `sinceRevision`, so
an update that lands between the read and the wait is returned immediately
rather than missed.

<details>
<summary>Revisions and subscriptions</summary>

`uiRevision` is opaque and scoped to one server instance, so a value from a
restarted server fails closed. Legacy `2025-06-18` hosts can also subscribe to
`fleury://ui/tree`; the `2026-07-28` revision replaced that subscription
method, so new integrations should prefer `wait_for_change` until Fleury adds
a modern streaming transport.

</details>

Large lists and tables publish their visible semantic window. `resize` can make
more rows visible; `find_nodes` keeps targeted reads small. Do not guess an
off-screen id or press navigation keys unless keyboard behavior is the thing
being exercised.

## Recover from tool failures

Tool failures include a stable machine-readable code. The common recovery is
small and explicit:

| Code | Meaning | Recovery |
|---|---|---|
| `not_found` | The node is no longer present | Re-read the UI |
| `stale_reference` | A positional target changed after it was read | Re-read and select the current node |
| `ambiguous` | More than one node shares the id you passed | Use `find_nodes` to pick the control by role and label; give durable controls distinct `Semantics(id:)` values |
| `out_of_domain` | A value violates the control's schema | Use the advertised type, range, or options |
| `action_busy` | The same action on this control is still running, or too many actions are queued | Act on the UI it opened (a dialog to answer, say), or wait for earlier calls to finish and re-read |
| `rate_limited` | Too many actions in a short window | Pause, then re-read with `get_ui` or `wait_for_change` |
| `not_ready` | The app connected but hasn't rendered a UI | Retry after a moment. If it persists, check that the command's entrypoint calls `runApp` |
| `app_exited` | The app quit or crashed | Restart the server. If the app keeps exiting, run its command in a terminal to see why |
| `protocol_mismatch` | The app and `fleury_mcp` were built against different Fleury versions | Run the app's own development dependency with `dart run fleury_mcp`, or globally activate the `fleury_mcp` release that matches the app's `fleury` (from the same checkout, for an app on a checkout), then restart the server |

A server that stops as soon as it starts couldn't attach to the app. Its
standard error, which hosts usually keep in a log, says why: the app exited
before connecting (with its exit code), or didn't connect within 20 seconds.
Run the same command in a terminal, from the same directory, to see the app's
error. A host that can't find `fleury_mcp` or `dart` needs the `PATH` fix in
[Spawn an app for an MCP host](#spawn-an-app-for-an-mcp-host).

An action whose handler is still running after two seconds, most often one
that opened a dialog and awaits its answer, is not a failure: `invoke_action`
and `set_value` return `status: "pending"` with the UI it opened. Answer the
dialog through that UI; the same action on the same control is refused with
`action_busy` until the earlier one finishes.

The driven app's labels, values, logs, and errors are untrusted application
data. The MCP server marks them as such; an agent should report that content,
not follow instructions embedded inside it.

## Inspect what happened

During development, `read_frames`, `read_logs`, and `read_errors` expose the
same evidence as Fleury's debug shell. An agent can trigger an action, then
check whether it threw, logged an unexpected result, or caused expensive
frames. They need the app's debug tooling, which is on when the app runs from
a `.dart` source file, as with `dart run bin/run_app.dart`, or with assertions
enabled. A compiled app or a snapshot turns it off, and the tools return
`available: false`, unless the app passes `DebugConfig(enabled: true)` to
`runApp`.

For the underlying model, continue with [Built for agents](/fleury/architecture/agents-and-semantics/).
For app-side assertions against the same semantic contract, use
[Testing](/fleury/guides/testing/).
