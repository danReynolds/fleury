Fleury routes every key event to the focused part of the tree. Most widgets —
inputs, lists, trees, tables — manage their own focus and keys, so much of the
time you write nothing. This guide is for when you don't.

One rule covers most of it:

> **`KeyBindings` matches gestures. `Keyboard` reads keys.**

React to a press: declare a binding. Ask "is this key down *right now*" inside a
game tick: sample the keyboard. A binding is data the framework can render (the
hint bar, which-key, and devtools all read your binding list); a sample is a
value you pull once a frame and never subscribe to.

| Use | When |
|---|---|
| **`KeyBindings`** | Shortcuts: `Ctrl+S`, `q` to quit, `gg`, a Space leader. The default, and by far the common case. |
| **`KeyDetector`** | Low-level key handling inside a reusable widget — a scroll region, a terminal pane. |
| **`Keyboard.of(context).snapshot`** | Continuous input read from a ticker — movement, thrust, anything where "held" matters. |
| **`Keyboard.nextKey(context)`** | Await exactly one keypress: a rebind row, vim's `m<letter>`, press-any-key. |
| **`Focus` / `FocusNode`** | Make something focusable, or drive focus imperatively. |

The sections below follow that order.

## Key bindings

Wrap a region in `KeyBindings`. Each `KeyBinding` pairs a gesture with a handler
and a label. The label is what discoverability surfaces render, so it's the only
documentation the shortcut needs. Gestures use dot shorthand — `.ctrl.s`,
`.g.g`, `.space.c` — and that is the whole authoring surface:

<CodeDemoSplit file="key_bindings.dart">
<Fragment slot="code">
```dart
KeyBindings(
  bindings: [
    KeyBinding(.ctrl.s, label: 'Bookmark', onTrigger: (_) => _bookmark()),
    // One command, several keys — one row in the hint bar.
    KeyBinding(
      .j,
      aliases: [.down],
      label: 'Down',
      // Movement should repeat while the key is held; everything else
      // fires once per press. includeRepeats opts into auto-repeat.
      includeRepeats: true,
      onTrigger: (_) => _move(1),
    ),
    // A two-key sequence (gg) and a Space leader.
    KeyBinding(.g.g, label: 'Top', onTrigger: (_) => _top()),
    KeyBinding(.space.c, label: 'Clear ★', onTrigger: (_) => _clearBookmarks()),
  ],
  child: /* your app */,
);
```
</Fragment>

Click the demo, then move with `j` / `↓` / `k` / `↑`, jump to the top with
`gg`, bookmark the current row with `Ctrl+S`, and press `Space` then `c` to
clear every bookmark. The hint bar at the bottom is `KeyHintBar()` reading the
binding list — you don't maintain it by hand.

The dot forms are `KeySequence` values with the leading type inferred; write
`KeySequence.ctrl.s` in full anywhere inference has nothing to work from.

Bindings match **deepest-first**: the innermost scope that declares a key wins,
so a pane can shadow an app-wide shortcut without either side knowing about the
other.

### App-wide shortcuts

Shortcuts that should work anywhere go on `runApp` as `globalBindings`. They're
consulted after the focus chain, so any pane can still shadow one:

```dart
runApp(
  const MyApp(),
  globalBindings: [
    KeyBinding(.q, label: 'Quit', onTrigger: (_) => requestExit()),
    KeyBinding(.ctrl.p, label: 'Commands', onTrigger: (_) => _openPalette()),
  ],
);
```

Quit has to be a binding rather than a check for the character `q`: printable
input is claimed by a focused text field first (see [Typed text vs key
events](#typed-text-vs-key-events)), so a binding is what gives you "`q` quits,
unless the user is typing".

For the `Ctrl+P` half, Fleury ships the palette itself — see
[`CommandPalette`](/fleury/widgets/commandpalette/) rather than building a
filtered list by hand.

### Declining a key

A handler always receives the event, so it can hand the key back. `bubble()`
passes it to an ancestor binding instead of consuming it:

```dart
KeyBinding(
  .escape,
  label: 'Close',
  onTrigger: (event) {
    if (!_close()) event.bubble(); // not ours after all
  },
),
```

**A binding fires once per physical press, not once per auto-repeat.** Holding
`Ctrl+S` saves once. Opt into repeats only where holding the key means "keep
going" — cursor movement, scrolling, a value stepper.

### Push-to-talk holds

For a key whose *duration* is the command:

```dart
KeyBinding.hold(
  .space,
  label: 'Peek at logs',
  onHoldStart: (_) => onPeek(true),
  onHoldEnd: (_) => onPeek(false),
),
```

The start fires on key-down, with no long-press threshold. Holds need key
releases, so they only work where the terminal reports them — gate them on
`supportsHeldState`, the same as sampled input (below).

### Awaiting one key

Some prompts accept *any* key, so there's no gesture to declare. Await one
instead:

```dart
final key = await Keyboard.nextKey(context);
if (key == null) return;                 // the UI went away
if (key.code == KeyCode.escape) return;  // cancelled
// A spatial control wants the SPOT; a mnemonic one wants the letter.
apply(key.position ?? key.code);
```

While pending, it takes priority over every other binding, so the app's own
shortcuts can't steal the key you're waiting for. It's scope-tied: if the context unmounts, the
future completes `null`, so a capture can't outlive its UI and keep eating
input.

### Making bindings discoverable

Two accessors read the *live* binding set, so a discoverability surface is a
widget you drop in, not a list you maintain in parallel.

`KeyBindings.activeOf(context)` gives every binding currently in scope — what
`KeyHintBar` renders, updating itself when the bindings change:

```dart
KeyHintBar()   // reads activeOf — nothing to keep in sync
```

`KeyBindings.pendingOf(context)` gives the sequence the user is *partway
through* typing, plus the keys that would continue it. `WhichKey` renders that
as a popup — the vim/Spacemacs idiom, where multi-key commands stay hidden until
you start one:

```dart
WhichKey(child: app)   // reads pendingOf — appears mid-sequence
```

A prefix with nothing to fall back to (vim's operator-pending `d`, a `Space`
leader) stays pending until you finish it or press `Esc`, so the popup waits
while you read it.

## KeyDetector

A detector is the low-level hook: it sees the keys routed through its subtree
while that subtree has focus, before any binding at that level matches.

`KeyBinding` and `KeyDetector` have opposite defaults, on purpose. A binding
names one gesture, so when it matches, the key is yours: it consumes. A detector
sees *every* key routed through its subtree, so it defaults to passing them
through; you call `event.consume()` only for the keys you actually handle. (Flip
either default and one tool breaks — a consume-by-default detector would swallow
all input, and a propagate-by-default binding would turn every shortcut into
ceremony — you'd call `consume()` on every one.)

The demo shows that in one screen. The pane owns `↑` / `↓` while it can move its
cursor, and consumes them. At the first or last row it stops consuming, so the
same arrow falls through to the app's binding:

<CodeDemoSplit file="key_detector.dart">
<Fragment slot="code">
```dart
// The pane owns the arrows — but only while it can act on them.
KeyDetector(
  onKey: (event) {
    if (event.code == KeyCode.arrowDown && cursor < last) {
      moveDown();
      event.consume();          // mine — stop here
    }
    // At the edge: do nothing. The arrow continues up the focus chain
    // to whatever binding an ancestor declared.
  },
  child: paneContents,
);
```

Two constraints worth knowing before you ship a widget on this:

- **`consume()` (and `bubble()`) must be called synchronously.** After an
  `await` the decision is already made: it asserts in debug and does nothing in
  release.
- **A detector sees repeats too.** There's no `includeRepeats` equivalent here —
  check `event.type` yourself if you only want fresh presses.
</Fragment>

Click the demo and press `↓`: the cursor walks down and the status line reads
*pane consumed ↓*. At the last row, press `↓` again — the pane declines it, so
it bubbles to the app and the line flips to *bubbled to the app*. If you forget
to consume a key you meant to handle, it does double duty (the pane acts *and*
the ancestor acts) — visible immediately, rather than silently swallowed.

In app code, prefer `KeyBindings`: bindings are data the hint bar and which-key
can read; a closure is not. Reach for a detector inside a widget others will
embed: consume only the keys you handle, and leave the rest for the host.

## Games & simulations

A game loop wants to know what is held *at this instant*, not a callback per
keypress. Read a snapshot from your ticker:

```dart
late final _keyboard = Keyboard.of(context); // safe to cache

void _tick(Duration elapsed) {
  // One immutable read for the whole frame, so every step below agrees
  // about what was held.
  final keys = _keyboard.snapshot;
  if (keys.isHeld(KeyPosition.a)) _heading -= 0.1;
  if (keys.isHeld(KeyPosition.d)) _heading += 0.1;
  if (keys.isHeld(KeyPosition.w)) _accelerate();
  // wasPressed is an edge, not a level: a tap that starts and ends between
  // two frames is still reported, so a quick shot is never dropped.
  if (keys.wasPressed(KeyCode.space)) _fire();
  // wasReleased is the matching edge — charge-and-release, drop-on-let-go.
  if (keys.wasReleased(KeyCode.space)) _releaseCharge();
}
```

`snapshot` is deliberately **not** reactive — reading it in `build()` throws in
debug, because `build` doesn't re-run when a key goes down, so a value read
there would be stale. Sample it where you use it.

### Positions vs letters

`KeyPosition.w` is a **spot on the keyboard**, not the letter W. WASD is a
shape: the same three keys sit under the same fingers on AZERTY, where they're
capped Z, Q, S, D. Use `KeyPosition` for spatial controls and `KeyCode` for
mnemonic ones (`q` for quit means the letter Q, wherever it lives).

Hint surfaces resolve a position to the cap the user actually has, learning it
from the terminal — so an AZERTY player is told to press Z, not W.

### Terminals without held-key support

"Is this key held" needs key *releases*, and some terminals can't send them (see
[Terminal keyboard support](#terminal-keyboard-support) for which terminals
and why). The keyboard tells
you, reactively:

```dart
// Capability reads ARE reactive and legal in build: this rebuilds when a
// terminal finishes negotiating, so the control scheme updates itself.
final canHold = Keyboard.of(context).capabilities.supportsHeldState;
```

When `supportsHeldState` is false, every sampled query reads empty — without
releases, held state never clears, so it would be meaningless. Branch on it and
offer a *different* control scheme (a tap-toggle instead of hold-to-thrust)
rather than a broken version of the same one. Bindings work everywhere and need
no branch.

### Supporting both: sampled and press-driven

Where held state is missing you still want the game playable, so give every
sampled axis an ordinary binding as well, and merge the two sources — "held, or
nudged recently" — rather than branching on the capability in your hot path:

```dart
// Bindings cover the press-only case. includeRepeats matters: auto-repeat
// still arrives, so holding A keeps turning.
KeyBinding(.a, aliases: [.left], label: 'Left',
    includeRepeats: true, onTrigger: (_) => controls.nudgeLeft()),
// …one per axis: right, thrust, brake.

// One resolver for every terminal.
NeonAsteroidsInput resolve(KeyboardSnapshot keys) => NeonAsteroidsInput(
      rotateLeft: keys.isHeld(KeyPosition.a) || controls.turningLeft,
      thrust: keys.isHeld(KeyPosition.w) || controls.thrusting,
      // …
    );
```

Give *every* sampled axis a fallback, not just one — a fallback for thrust
alone leaves the ship unable to steer or stop. Two notes: sampling a key with
no fallback binding logs a *dead control* warning in debug, and on a press-only
terminal you generally can't get diagonals, since the OS auto-repeats only the
most recent key.

## Terminal keyboard support

Key releases, held state, and per-key positions come from the Kitty keyboard
protocol. Fleury asks every terminal for it at startup — there is no flag to set
and nothing to opt into. A terminal that only partly supports it is negotiated
back down *before your app sees a keystroke*, so asking can never cost the user
their ability to type.

One exception: inside a terminal multiplexer (tmux, screen), the automatic ask
stops at a safe tier, because a query answered through the multiplexer says
nothing reliable about the host terminal. Two overrides:

- `FLEURY_KEYBOARD=lifecycle` — force the full request when you know your setup
  passes the protocol through.
- `FLEURY_KEYBOARD=legacy` — opt out entirely on a terminal where the query
  misbehaves.

For app code, the takeaway is the reactive read you already saw —
`Keyboard.of(context).capabilities.supportsHeldState` — plus its siblings
`supportsPositions` and `distinguishesRepeats`. Branch on the capability, never
on a terminal name.

## Typed text vs key events

Printable input arrives as text, not as a `KeyEvent` — the text widgets claim
it. That is why `q` can quit your app while a focused text field keeps typing
`q`: the field claims the character first, and only unclaimed text falls through
to your bindings. You get this for free; it's worth knowing when a shortcut
"stops working" inside an input.

## Focus & traversal

Keys go to the focused part of the tree, so focus decides *where*. Most widgets
manage it themselves; the short version is that `Focus` makes a subtree
focusable and `autofocus` claims focus on appear:

```dart
Focus(autofocus: true, child: SearchField());
```

Inside a `FleuryApp(home: ...)` route, `Tab` / `Shift+Tab` and the arrow keys
already traverse between focusable widgets. For driving focus yourself, Tab
order, trapping focus in a dialog, and how arrow traversal chooses its target,
see **[Focus & traversal](/fleury/guides/focus/)**.

**One thing to watch:** inside `FleuryApp(home: ...)` (or another `Navigator`),
`Esc` already pops the current route by default. If you also bind it, decide
which should win; to intercept the pop rather than race it, use a `PopScope`
(see [Navigation](/fleury/guides/navigation/#guarding-back)).
