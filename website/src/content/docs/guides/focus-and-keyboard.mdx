Keyboard support is built into Fleury's widgets. A `ListView` already responds
to the arrow keys, a `TextInput` already edits text, and buttons already react
to their activation keys. You add keyboard handling when your application has
its own commands: save, quit, open a palette, move a cursor, or control a game.

For most applications, the answer is `KeyBindings`. You declare a gesture, its
label, and what it does. Fleury routes the gesture through the focused part of
the widget tree, chooses the nearest matching binding, and exposes the same
declaration to shortcut hints.

There are two lower-level tools for specialized work:

| You need to… | Use |
|---|---|
| Run a command for a known key or sequence | `KeyBinding` inside `KeyBindings` |
| Handle keys internally while building a reusable widget | `KeyDetector` |
| Read what is currently held during a game or simulation tick | `Keyboard.snapshot` |

This guide starts with the common command path, then covers those lower-level
cases. To control *where* keys go—focusable widgets, Tab order, and traversal—see
[Focus management](/fleury/guides/focus/).

## Core commands

### Declare a shortcut

Wrap the part of the application that owns the command in `KeyBindings`, then
add a `KeyBinding`:

```dart
KeyBindings(
  bindings: [
    KeyBinding(
      .ctrl.s,
      label: 'Save',
      onTrigger: (_) => save(),
    ),
  ],
  child: const Editor(),
);
```

The gesture uses `KeySequence` dot shorthand. In a context where Dart cannot
infer the type, write it in full as `KeySequence.ctrl.s`.

Bindings fire once per physical press by default, so holding `Ctrl+S` still
saves once. The label is part of the declaration because Fleury uses it for
discoverability surfaces such as `KeyHintBar`.

### Scope shortcuts

Put application-wide shortcuts near the root:

```dart
runApp(
  KeyBindings(
    bindings: [
      KeyBinding(.q, label: 'Quit', onTrigger: (_) => requestExit()),
      KeyBinding(.ctrl.p, label: 'Commands', onTrigger: (_) => openPalette()),
    ],
    child: const MyApp(),
  ),
);
```

Add another `KeyBindings` around a pane, screen, or control when commands are
local to that region. Fleury checks the focused chain **deepest-first**, so the
nearest declaration wins. An editor can give `Ctrl+S` a local meaning while the
rest of the application keeps its own binding, without either scope knowing
about the other.

### Aliases, sequences, and repeat

A command can accept aliases, use more than one key, or opt into auto-repeat.
This example combines the common forms:

```dart
KeyBindings(
  bindings: [
    KeyBinding(.ctrl.s, label: 'Bookmark', onTrigger: (_) => bookmark()),
    KeyBinding(
      .j,
      aliases: [.down],
      label: 'Down',
      includeRepeats: true,
      onTrigger: (_) => move(1),
    ),
    KeyBinding(.g.g, label: 'Top', onTrigger: (_) => goToTop()),
    KeyBinding(.space.c, label: 'Clear ★', onTrigger: (_) => clearBookmarks()),
  ],
  child: app,
);
```

Click the running example, then try these commands:

- Move with `j` / `↓` and `k` / `↑`. Holding a movement key repeats because

- Press `gg` to jump to the top.
- Press `Ctrl+S` to bookmark the selected row.
- Press `Space`, then `c`, to clear the bookmarks.

Aliases describe several gestures for one command, so they produce one entry in
the hint bar. Sequences such as `gg` and `Space c` remain pending briefly while
Fleury waits for the next key.

### Shortcut discovery

`KeyHintBar` reads the bindings active at its location. You do not maintain a
second list of shortcut labels:

```dart
KeyHintBar()
```

For multi-key sequences, wrap the application in `WhichKey`. It reads the
pending sequence and shows the possible continuations:

```dart
WhichKey(child: app)
```

The editor below uses both patterns. Click it, press `Ctrl+B` to switch from the
nano keymap to the vim keymap, then press `d`, `g`, or `Space` and pause to see
the available continuations.

and the surface presenting it do. See the [editor walkthrough](/fleury/showcases/editor/)

### Text input precedence

Printable input is offered to focused text widgets before it becomes a command.
That is why a root binding can make `q` quit while a focused `TextInput` still
types the letter `q`. The field claims the text; only unclaimed input continues
through the binding chain.

Use bindings for commands rather than manually checking characters. You then
get the expected "`q` quits unless the user is typing" behavior without adding
focus checks to every handler.

## Advanced patterns

The rest of this guide is for reusable controls, real-time input, and commands
whose lifecycle is more involved than a single press. Most application
shortcuts do not need these APIs.

### Custom widget handling

`KeyDetector` is the low-level hook for behavior internal to a widget: a custom
scroll region, canvas, or terminal pane. It sees keys routed through its subtree
while that subtree has focus.

A detector passes events onward by default. Call `consume()` only when the
widget actually handled the key. This lets a scrollable control own `↓` while it
can move and hand the same key to an ancestor when it reaches the bottom:

<CodeDemoSplit file="key_detector.dart">
<Fragment slot="code">
```dart
KeyDetector(
  onKey: (event) {
    if (event.code == KeyCode.arrowDown && cursor < last) {
      moveDown();
      event.consume();
    }
    // At the edge, leave the event unconsumed so an ancestor can handle it.
  },
  child: paneContents,
);
```
</Fragment>
<Fragment slot="demo">
<FleuryExample id="keydetector.basic" cols={64} rows={12} interactive />
</Fragment>
</CodeDemoSplit>

Click the example and press `↓` three times. Its event trace makes the routing
visible: the pane handles the first two presses and moves its cursor, so the app
is not reached. On the third press, the pane is at its edge and passes the key;
the ancestor app binding handles it. Press `↑` to watch the same path in reverse.

Two rules matter when implementing a detector:

- Call `consume()` synchronously. After an `await`, the routing decision has
  already been made.
- Detectors receive repeats. Check `event.type` if the widget only handles
  fresh presses.

Prefer `KeyBindings` in ordinary application code: declarations can drive
shortcut hints and inspection tools; an arbitrary detector callback cannot.

### Real-time held keys

A real-time loop usually wants the current keyboard state once per frame rather
than one callback per keypress. Cache the keyboard handle and take one immutable
snapshot per tick:

```dart
late final _keyboard = Keyboard.of(context);

void tick(Duration elapsed) {
  final keys = _keyboard.snapshot;
  if (keys.isHeld(KeyPosition.a)) heading -= 0.1;
  if (keys.isHeld(KeyPosition.d)) heading += 0.1;
  if (keys.isHeld(KeyPosition.w)) accelerate();
  if (keys.wasPressed(KeyCode.space)) fire();
}
```

`isHeld` reports a level. `wasPressed` and `wasReleased` report edges, so a quick
press and release between two frames is not lost. Read `snapshot` in the loop
that consumes it, not in `build()`; snapshots are intentionally non-reactive.

Held state depends on key-release events, which are not available on every
terminal. Read the reactive capability in `build` and provide a press-driven
fallback:

```dart
final canHold = Keyboard.of(context).capabilities.supportsHeldState;

KeyBinding(
  .a,
  aliases: [.left],
  label: 'Left',
  includeRepeats: true,
  onTrigger: (_) => controls.nudgeLeft(),
);
```

Give every sampled control a fallback. On a press-only terminal, auto-repeat can
keep a single axis moving, but simultaneous held-key combinations may not be
available.

### Keyboard layouts

Use a `KeyPosition` when the control is spatial and should stay under the same
finger across keyboard layouts. Use a `KeyCode` when the command is mnemonic
and should follow the printed letter:

```dart
// Movement wants the physical spot used by W on QWERTY.
if (keys.isHeld(KeyPosition.w)) accelerate();

// "q for quit" wants the letter Q on every layout.
KeyBinding(.q, label: 'Quit', onTrigger: (_) => requestExit());
```

On AZERTY, the physical position used by QWERTY `W` is labeled `Z`. Fleury's
hint surfaces resolve positions to the user's label when that information is
available.

### Holds, bubbling, and capture

Use a hold binding when the duration itself is the command, such as
push-to-talk or peek-while-held. Only offer it when releases are supported:

```dart
KeyBindings(
  bindings: [
    if (Keyboard.of(context).capabilities.supportsHeldState)
      KeyBinding.hold(
        .space,
        label: 'Peek at logs',
        onHoldStart: (_) => setPeeking(true),
        onHoldEnd: (_) => setPeeking(false),
      ),
  ],
  child: content,
);
```

A matching binding normally consumes its event. A handler can decline after it
runs by calling `bubble()`, which hands the event to an ancestor binding:

```dart
KeyBinding(
  .escape,
  label: 'Close',
  onTrigger: (event) {
    if (!close()) event.bubble();
  },
);
```

For rebinding controls or prompts that accept any key, await the next event:

```dart
final key = await Keyboard.nextKey(context);
if (key == null || key.code == KeyCode.escape) return;
apply(key.position ?? key.code);
```

The capture takes priority over ordinary bindings and is tied to its
`BuildContext`. If that UI unmounts, the future completes with `null` rather
than continuing to consume input.

### Terminal support

Most shortcuts need no terminal-specific code. Fleury automatically negotiates
enhanced keyboard input and falls back to classic press events, so commands such
as `Ctrl+S`, `q`, arrows, and multi-key sequences use the same declarations on
both paths.

Check a capability only when the feature fundamentally needs information that a
classic terminal may not deliver. This control uses hold-to-peek when reliable
releases are available, and keeps Space useful as a press-to-toggle fallback
when they are not:

```dart
final canHold = Keyboard.of(context).capabilities.supportsHeldState;

KeyBindings(
  bindings: [
    if (canHold)
      KeyBinding.hold(
        .space,
        label: 'Peek (hold)',
        onHoldStart: (_) => setPeeking(true),
        onHoldEnd: (_) => setPeeking(false),
      )
    else
      KeyBinding(
        .space,
        label: 'Peek (toggle)',
        onTrigger: (_) => setPeeking(!peeking),
      ),
  ],
  child: content,
);
```

Capability reads in `build` are reactive: if startup negotiation upgrades the
session, Fleury rebuilds the control and selects the hold gesture. The
[Neon Asteroids example above](#real-time-held-keys) uses this same decision for
continuous flight controls while retaining press-driven movement as its
fallback.

Fleury supports enhanced terminal input through the Kitty keyboard protocol.
The framework requests it automatically, confirms the guarantees the terminal
and any multiplexer actually preserve, and exposes only those semantic
capabilities to the app. Application code should not inspect terminal names,
parse protocol replies, or force a keyboard mode.

For diagnostics and operator-level overrides, see
[Terminal capabilities](/fleury/guides/terminal-capabilities/). Terminal and
framework authors can find the wire-level format in the
[Kitty keyboard protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/).

## Next steps

The default is deliberately small: use `KeyBindings` for commands, place them
at the scope that owns them, and render the same declarations with
`KeyHintBar` or `WhichKey`. Reach for `KeyDetector` only inside a custom
keyboard-aware widget, and for `Keyboard.snapshot` only when a real-time loop
needs held state.
