You handle keys in Fleury by declaring what you want: a key or a sequence,
paired with a handler and a label. Fleury matches those declarations against the
focused part of the tree, and the same list drives the hint bar, so your
shortcuts stay documented as you add them.

Most widgets already handle their own keys — you write nothing for a list to
respond to `↓`. This guide covers the rest: app shortcuts, keys inside a widget
you're building, and real-time input for games. For where keys *go* — focusable
widgets, Tab order, traversal — see
[Focus management](/fleury/guides/focus/).

## Key bindings

Wrap a region in `KeyBindings`. Each `KeyBinding` pairs a gesture with a handler
and a label. The label is what discoverability surfaces render, so it's the only
documentation the shortcut needs. Gestures use dot shorthand — `.ctrl.s`,
`.g.g`, `.space.c`:

<CodeDemoSplit file="key_bindings.dart">
<Fragment slot="code">
```dart
KeyBindings(
  bindings: [
    KeyBinding(.ctrl.s, label: 'Bookmark', onTrigger: (_) => _bookmark()),
    // One command, several keys — one row in the hint bar.
    KeyBinding(
      .j,
      aliases: [.down],
      label: 'Down',
      // Movement should repeat while the key is held; everything else
      // fires once per press. includeRepeats opts into auto-repeat.
      includeRepeats: true,
      onTrigger: (_) => _move(1),
    ),
    // A two-key sequence (gg) and a Space leader.
    KeyBinding(.g.g, label: 'Top', onTrigger: (_) => _top()),
    KeyBinding(.space.c, label: 'Clear ★', onTrigger: (_) => _clearBookmarks()),
  ],
  child: /* your app */,
);
```
</Fragment>

Click the demo, then move with `j` / `↓` / `k` / `↑`, jump to the top with
`gg`, bookmark the current row with `Ctrl+S`, and press `Space` then `c` to
clear every bookmark. The hint bar at the bottom is `KeyHintBar()` reading the
binding list — you don't maintain it by hand.

The dot forms are `KeySequence` values with the leading type inferred; write
`KeySequence.ctrl.s` in full anywhere inference has nothing to work from.

**A binding fires once per physical press, not once per auto-repeat.** Holding
`Ctrl+S` saves once. Opt into repeats only where holding the key means "keep
going" — cursor movement, scrolling, a value stepper.

Bindings match **deepest-first**: the innermost scope that declares a key wins,
so a pane can shadow an app-wide shortcut without either side knowing about the
other.

### App-wide shortcuts

Shortcuts that work anywhere are a `KeyBindings` near the root of your app — the
outermost scope, so anything deeper can still shadow it:

```dart
runApp(
  KeyBindings(
    bindings: [
      KeyBinding(.q, label: 'Quit', onTrigger: (_) => requestExit()),
      KeyBinding(.ctrl.p, label: 'Commands', onTrigger: (_) => _openPalette()),
    ],
    child: const MyApp(),
  ),
);
```

Quit has to be a binding rather than a check for the character `q`: printable
input is claimed by a focused text field first (see [Typed text vs key
events](#typed-text-vs-key-events)), so a binding is what gives you "`q` quits,
unless the user is typing".

For the `Ctrl+P` half, Fleury ships the palette itself — see
[`CommandPalette`](/fleury/widgets/commandpalette/) rather than building a
filtered list by hand.

`runApp` also takes a `globalBindings` list, consulted after the whole focus
chain rather than as part of it. Prefer the widget: it participates in scoping
and the hint bar picks it up automatically.

### Making bindings discoverable

`KeyBindings.activeOf(context)` gives every binding currently in scope, so a
hint surface is a widget you drop in rather than a list you maintain in
parallel:

```dart
KeyHintBar()   // reads activeOf — nothing to keep in sync
```

For multi-key sequences, `KeyBindings.pendingOf(context)` gives what the user is
partway through typing plus the keys that would continue it — the vim/Spacemacs
which-key idiom, rendered by `WhichKey(child: app)`.

The editor sample runs both. Press **Ctrl+B** to swap between a nano keymap and
a vim one over the same buffer, then press `d`, `g`, or `Space` in vim mode and
pause:

## KeyDetector

A detector is the low-level hook: it sees the keys routed through its subtree
while that subtree has focus, before any binding at that level matches. Reach
for it when the handling is internal to a widget others will embed — a scroll
region, a terminal pane forwarding raw keys.

`KeyBinding` and `KeyDetector` have opposite defaults, on purpose. A binding
names one gesture, so when it matches, the key is yours: it consumes. A detector
sees *every* key in its subtree, so it defaults to passing them through; you
call `event.consume()` only for the keys you actually handle.

The demo shows that in one screen. The pane owns `↑` / `↓` while it can move its
cursor, and consumes them. At the first or last row it stops consuming, so the
same arrow falls through to the app's binding:

<CodeDemoSplit file="key_detector.dart">
<Fragment slot="code">
```dart
// The pane owns the arrows — but only while it can act on them.
KeyDetector(
  onKey: (event) {
    if (event.code == KeyCode.arrowDown && cursor < last) {
      moveDown();
      event.consume();          // mine — stop here
    }
    // At the edge: do nothing. The arrow continues up the focus chain
    // to whatever binding an ancestor declared.
  },
  child: paneContents,
);
```
</Fragment>
<Fragment slot="demo">
<FleuryExample id="keyboard.detector" cols={64} rows={12} interactive />
</Fragment>
</CodeDemoSplit>

Click the demo and press `↓`: the cursor walks down and the status line reads
*pane consumed ↓*. At the last row, press `↓` again — the pane declines it, so
it bubbles to the app and the line flips to *bubbled to the app*.

Two constraints before you ship a widget on this:

- **`consume()` must be called synchronously.** After an `await` the decision is
  already made: it asserts in debug and does nothing in release.
- **A detector sees repeats too.** There's no `includeRepeats` equivalent here —
  check `event.type` yourself if you only want fresh presses.

In app code, prefer `KeyBindings`: bindings are data the hint bar can read; a
closure is not.

## Let's build a game

Games want different things from the keyboard than apps do. Three capabilities
carry most of it.

**Read what's held, once per frame.** A game loop doesn't want a callback per
keypress — it wants to know what's down *right now*. Sample the keyboard from
your ticker:

```dart
late final _keyboard = Keyboard.of(context); // safe to cache

void _tick(Duration elapsed) {
  // One immutable read for the whole frame, so every step below agrees
  // about what was held.
  final keys = _keyboard.snapshot;
  if (keys.isHeld(KeyPosition.a)) _heading -= 0.1;
  if (keys.isHeld(KeyPosition.d)) _heading += 0.1;
  if (keys.isHeld(KeyPosition.w)) _accelerate();
}
```

`snapshot` is deliberately **not** reactive — reading it in `build()` throws in
debug, because `build` doesn't re-run when a key goes down, so a value read
there would be stale. Sample it where you use it.

**Catch taps that fall between frames.** `wasPressed` and `wasReleased` are
*edges*, not levels: a press and release that land entirely between two frames
are still reported, so a quick shot is never dropped.

```dart
if (keys.wasPressed(KeyCode.space)) _fire();
if (keys.wasReleased(KeyCode.space)) _releaseCharge();
```

**Handle terminals that can't report held keys.** Held state needs key
releases, which not every terminal sends. The capability is reactive and legal
in `build`:

```dart
final canHold = Keyboard.of(context).capabilities.supportsHeldState;
```

Where it's false every sampled query reads empty, so pair each sampled axis with
an ordinary binding and merge the two — "held, or nudged recently":

```dart
// includeRepeats matters: auto-repeat still arrives, so holding A keeps
// turning even without held-state support.
KeyBinding(.a, aliases: [.left], label: 'Left',
    includeRepeats: true, onTrigger: (_) => controls.nudgeLeft()),

NeonAsteroidsInput resolve(KeyboardSnapshot keys) => NeonAsteroidsInput(
      rotateLeft: keys.isHeld(KeyPosition.a) || controls.turningLeft,
      thrust: keys.isHeld(KeyPosition.w) || controls.thrusting,
    );
```

Give *every* sampled axis a fallback, not just one — a fallback for thrust alone
leaves the ship unable to steer or stop. Sampling a key with no fallback logs a
*dead control* warning in debug. And on a press-only terminal you generally
can't get diagonals, since the OS auto-repeats only the most recent key.

### Positions vs letters

`KeyPosition.w` is a **spot on the keyboard**; `KeyCode.w` is the **letter W**.
WASD is a shape — the same three keys sit under the same fingers on AZERTY,
where they're capped Z, Q, S, D:

```dart
// Movement wants the SHAPE. On AZERTY this is the key capped Z — where
// that player's finger already rests.
if (keys.isHeld(KeyPosition.w)) _accelerate();

// A mnemonic command wants the LETTER. "q for quit" should be the Q key
// wherever the layout puts it.
KeyBinding(.q, label: 'Quit', onTrigger: (_) => requestExit());
```

Hint surfaces resolve a position to the cap the user actually has, learning it
from the terminal — so an AZERTY player is told to press Z, not W.

## Keyboard protocol support

Plain terminal input is thin: bytes on press, nothing on release, and no way to
tell `Ctrl+I` from `Tab`. The [Kitty keyboard
protocol](https://sw.kovidgoyal.net/kitty/keyboard-protocol/) fixes that — key
releases, unambiguous chords, per-key positions — and Fleury negotiates it for
you.

At startup Fleury requests the full protocol, then **verifies what the terminal
actually honors**. One that supports only part of it is negotiated back down
*before your app sees a keystroke*, so asking can never cost the user their
ability to type. There's no flag to set and nothing to opt into.

That verification earns its keep: a terminal can advertise key releases and then
never send them. Fleury catches the contradiction at runtime, demotes the
surface to press-only, releases the keys it had recorded as held, and updates
`capabilities` — so an app that branches on the capability re-branches live
rather than hanging on a key that never comes up.

| Capability | What it means |
|---|---|
| `supportsHeldState` | `isHeld` / `wasReleased` work — the terminal reports releases. |
| `supportsPositions` | `KeyPosition` resolves to real physical keys. |
| `distinguishesRepeats` | Auto-repeat is tagged, so `includeRepeats` is exact. |

Branch on the capability, never on a terminal name.

### Terminal limitations

Inside a multiplexer (tmux, screen) the automatic request stops at a safe tier,
because a query answered through the multiplexer says nothing reliable about the
host terminal. Two overrides:

- `FLEURY_KEYBOARD=lifecycle` — force the full request when you know your setup
  passes the protocol through.
- `FLEURY_KEYBOARD=legacy` — opt out entirely on a terminal where the query
  misbehaves.

Without the protocol you still get every press, every chord the legacy encoding
can express, and auto-repeat. What you lose is held state, releases, and
reliable positions — which is what the fallback pattern above is for.

## Typed text vs key events

Printable input arrives as text, not as a `KeyEvent` — the text widgets claim
it. That's why `q` can quit your app while a focused text field keeps typing
`q`: the field claims the character first, and only unclaimed text falls through
to your bindings. You get this for free; it's worth knowing when a shortcut
"stops working" inside an input.

## More binding options

**Canceling propagation.** A handler always receives the event, so it can hand
the key back. `bubble()` passes it to an ancestor binding instead of consuming
it:

```dart
KeyBinding(
  .escape,
  label: 'Close',
  onTrigger: (event) {
    if (!_close()) event.bubble(); // not ours after all
  },
),
```

**Holds.** For a key whose *duration* is the command — push-to-talk,
peek-while-held. The start fires on key-down with no long-press threshold, and
it needs key releases, so gate it on `supportsHeldState`:

```dart
KeyBinding.hold(
  .space,
  label: 'Peek at logs',
  onHoldStart: (_) => onPeek(true),
  onHoldEnd: (_) => onPeek(false),
),
```

**Awaiting one key.** Some prompts accept *any* key — a rebind row, vim's
`m<letter>` — so there's no gesture to declare:

```dart
final key = await Keyboard.nextKey(context);
if (key == null) return;                 // the UI went away
if (key.code == KeyCode.escape) return;  // cancelled
apply(key.position ?? key.code);
```

While pending it takes priority over every other binding, so the app's own
shortcuts can't steal the key you're waiting for. It's scope-tied: if the
context unmounts the future completes `null`, so a capture can't outlive its UI
and keep eating input.
