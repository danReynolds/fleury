Fleury routes every key event to the focused part of the tree. Most widgets —
inputs, lists, trees, tables — manage their own focus and keys, so much of the
time you write nothing. This guide is for when you don't.

One rule decides almost everything:

> **`KeyBindings` matches gestures. `Keyboard` reads keys.**

React to a press → declare a binding. Ask "is this key down *right now*" inside
a game tick → sample the keyboard. Those are different questions, and the API
keeps them apart on purpose: a binding is data the framework can render (the
hint bar, which-key, devtools all read your binding list), while sampled state
is a value you pull once a frame and never subscribe to.

| Use | When |
|---|---|
| **`KeyBindings`** | Shortcuts: `Ctrl+S`, `q` to quit, `gg`, a Space leader. The default and by far the common case. |
| **`KeyDetector`** | Conditional handling *inside a reusable widget* — a scroll region, a terminal pane. The propagating floor, not the authoring surface. |
| **`Keyboard.of(context).snapshot`** | Continuous input read from a ticker — movement, thrust, anything where "held" matters. |
| **`Keyboard.nextKey(context)`** | Await exactly one keypress: a rebind row, vim's `m<letter>`, press-any-key. |
| **`Focus` / `FocusNode`** | Make something focusable, or drive focus imperatively. |

The rest of this guide follows that order: the common case first, then the
floor beneath it, then the game-loop path, and finally the details worth
knowing when something surprises you.

## Key bindings — the common case

Wrap a region in `KeyBindings`. Each `KeyBinding` pairs a gesture with a
handler and a label — the label is what discoverability surfaces render, so
writing one is how your app teaches itself. Gestures are written in dot
shorthand — `.ctrl.s`, `.g.g`, `.space.c` — and this is the whole authoring
surface, running live:

<CodeDemoSplit file="key_bindings.dart">
<Fragment slot="code">
```dart
KeyBindings(
  bindings: [
    KeyBinding(.ctrl.s, label: 'Bookmark', onTrigger: (_) => _bookmark()),
    // One command, several keys — one row in the hint bar.
    KeyBinding(
      .j,
      aliases: [.down],
      label: 'Down',
      // Movement is the repeat-reliant class: holding the key
      // should keep moving. Everything else fires once per press.
      includeRepeats: true,
      onTrigger: (_) => _move(1),
    ),
    // A two-key sequence (gg) and a Space leader — try them in the demo.
    KeyBinding(.g.g, label: 'Top', onTrigger: (_) => _top()),
    KeyBinding(.space.c, label: 'Clear ★', onTrigger: (_) => _clearBookmarks()),
  ],
  child: child,
);
```
</Fragment>

Click the demo, then move with `j` / `↓` / `k` / `↑`, jump to the top with

the binding list — nothing is maintained by hand.

The dot forms are plain `KeySequence` values with the leading type inferred;
write `KeySequence.ctrl.s` longhand anywhere inference has nothing to infer
from.

Bindings match **deepest-first**: the innermost scope that declares a key wins,
so a pane can shadow an app-wide shortcut without either side knowing about the
other.

### Declining a key

```dart
// A handler always receives the event, so it can decline: bubble() hands
// the key to an ancestor binding instead of consuming it.
KeyBinding(
  .escape,
  label: 'Close',
  onTrigger: (event) {
    if (!_close()) event.bubble(); // not ours after all
  },
),
```

**A binding fires once per physical press, not once per auto-repeat.** Holding
`Ctrl+S` saves once. Opt into repeats only where holding the key genuinely
means "keep going" — cursor movement, scrolling, a value stepper.

### Modal scopes

A dialog should not let the app's shortcuts fire behind it. `modal: true` stops
the walk at that scope:

```dart
KeyBindings(
  modal: true,
  bindings: [
    KeyBinding(.y, label: 'Yes', onTrigger: (_) => onAnswer(true)),
    KeyBinding(.n, label: 'No', onTrigger: (_) => onAnswer(false)),
    KeyBinding(.escape, label: 'Cancel', onTrigger: (_) => onAnswer(false)),
  ],
  child: const Focus(autofocus: true, child: Text('Delete this file? y/n')),
);
```

### Push-to-talk holds

For a key whose *duration* is the command:

```dart
KeyBinding.hold(
  .space,
  label: 'Peek at logs',
  onHoldStart: (_) => onPeek(true),
  onHoldEnd: (_) => onPeek(false),
),
```

There is no long-press threshold: the start fires on the down, immediately.
Holds need key releases, so they only work where the terminal reports them —
gate them on `supportsHeldState` the same way sampled input does (below).

### Awaiting one key

Some prompts take *any* key — a rebind row, vim's `m<letter>`. Declaring 26
bindings would be a lie; await one instead:

```dart
final key = await Keyboard.nextKey(context);
if (key == null) return;                 // the UI went away
if (key.code == KeyCode.escape) return;  // cancelled
// A spatial control wants the SPOT; a mnemonic one wants the letter.
apply(key.position ?? key.code);
```

While it is pending it outranks every other lane, so the app's own bindings
cannot steal the key you are waiting for. It is scope-tied by signature: if the
context unmounts the future completes `null`, so a capture can never outlive its
UI and quietly eat the app's input.

### Let the app teach its own keys

Two accessors read the *live* binding set, so a discoverability surface is a
widget you drop in, not a list you maintain in parallel.

`KeyBindings.activeOf(context)` gives every binding currently in scope — what
`KeyHintBar` renders, updating itself when the bindings change:

```dart
KeyHintBar()   // reads activeOf — nothing to keep in sync
```

`KeyBindings.pendingOf(context)` gives the sequence the user is *partway
through* typing, plus the keys that would continue it. `WhichKey` renders that as
a popup — the vim/Spacemacs idiom, where multi-key commands stay hidden until you
start one:

```dart
WhichKey(child: app)   // reads pendingOf — appears mid-sequence
```

A prefix with nothing to fall back to (vim's operator-pending `d`, a `Space`
leader) stays pending until you finish it or press `Esc`, so the popup waits
while you read it.

## KeyDetector — the propagating floor

Reach for a detector when the handling is genuinely internal to a reusable
widget — a scroll region, a bridge, a terminal pane forwarding raw keys.
**A detector propagates by default**, the inverse of a binding: a binding
*declared* a match, so consuming is its meaning; a detector is peeking, so
observing is the base state. You consume only the keys you own, and everything
else keeps travelling up the focus chain.

That yield-at-the-boundary behaviour is the whole point, and it is what the demo
shows. The pane owns `↑` / `↓` while it can move its cursor and consumes them;
at the first or last row it *stops* consuming, so the same arrow falls through
to the app's own binding:

<CodeDemoSplit file="key_detector.dart">
<Fragment slot="code">
```dart
// The reusable pane owns the arrows — but only while it can act on them.
KeyDetector(
  onKey: (event) {
    if (event.code == KeyCode.arrowDown && cursor < last) {
      moveDown();
      event.consume();          // mine — stop here
    }
    // At the edge: do nothing. The arrow continues up the focus chain
    // to whatever binding an ancestor declared.
  },
  child: paneContents,
);
```
</Fragment>
<Fragment slot="demo">

Click the demo and hold `↓`: the pane's cursor walks down and the status line
reads *pane consumed ↓*. Reach the last row and press `↓` once more — the pane
declines it, so it bubbles to the app and the line flips to *bubbled to the
app*. Forget to consume and your key visibly does double duty while you test it,
instead of silently starving an ancestor.

Prefer `KeyBindings` in app code: bindings are data the hint bar and which-key
can read, and a closure is not. Reach for a detector inside a widget others
will embed, where "let the host keep what I don't use" is the contract.

## Games & simulations — sampling held keys

A game loop does not want a callback per keypress; it wants to know what is held
*at this instant*. Read a snapshot from your ticker:

```dart
late final _keyboard = Keyboard.of(context); // safe to cache

void _tick(Duration elapsed) {
  // ONE immutable read for the whole frame, so every step below agrees
  // about what was held.
  final keys = _keyboard.snapshot;
  if (keys.isHeld(KeyPosition.a)) _heading -= 0.1;
  if (keys.isHeld(KeyPosition.d)) _heading += 0.1;
  if (keys.isHeld(KeyPosition.w)) _accelerate();
  // An EDGE, not a level: a tap that starts and ends between two frames is
  // still reported, so a quick shot is never swallowed.
  if (keys.wasPressed(KeyCode.space)) _fire();
}
```

`snapshot` is deliberately **not** reactive — reading it in `build()` throws in
debug, because `build` is not re-run when a key goes down and a value read there
would be stale by construction. Sample it where you use it.

### Positions vs letters

`KeyPosition.w` names a **spot on the keyboard**, not the letter W. WASD is a
shape — the same three keys sit under the same fingers on AZERTY, where they are
capped Z, Q, S, D. Use `KeyPosition` for spatial controls and `KeyCode` for
mnemonic ones (`q` for quit means the letter Q, wherever it lives).

Hint surfaces resolve a position to the cap the user actually has, learning it
from the terminal where the protocol reports it — so an AZERTY player is told to
press Z, not W.

### When a terminal can't report held keys

"Is this key held" needs key *releases*, and some terminals cannot send them at
all (see [Terminal support](#terminal-support--the-keyboard-protocol) for the
full story of who can and why). The keyboard tells you, reactively:

```dart
// Capability reads ARE reactive and legal in build: this rebuilds when a
// terminal finishes negotiating, so the control scheme upgrades itself.
final canHold = Keyboard.of(context).capabilities.supportsHeldState;
```

Where `supportsHeldState` is false, every sampled query reads empty — an
accumulating set with no releases is a lying set. Branch on it and offer a
*different* control scheme (a tap-toggle instead of hold-to-thrust) rather than
a broken version of the same one. Bindings work everywhere and need no branch.

### One game, two control schemes

The production shape of that branch is a duet: the sampled scheme where held
state exists, and a **press-driven fallback built from ordinary bindings**
everywhere else. Bindings are the fallback on purpose — presses are the one
thing every terminal reports, and binding labels let the hint bar tell the
truth about which scheme is live:

```dart
Widget build(BuildContext context) {
  // Reactive: rebuilds when negotiation lands or a surface is demoted, so
  // the control scheme (and its hint labels) upgrade and downgrade live.
  final canHold = Keyboard.of(context).capabilities.supportsHeldState;
  return KeyBindings(
    bindings: [
      // Commands need no branch — they work on every tier.
      KeyBinding(.space, label: 'Fire', onTrigger: (_) => fire()),
      if (!canHold)
        // The fallback: each press nudges the simulation a fixed step, and
        // includeRepeats keeps it nudging while the key auto-repeats. The
        // label says what the control really is on THIS terminal.
        KeyBinding(
          KeyPosition.w,
          aliases: [KeyCode.arrowUp],
          label: 'Thrust (tap)',
          includeRepeats: true,
          onTrigger: (_) => controls.nudgeThrust(),
        ),
    ],
    child: playfield,
  );
}

void tick(Duration elapsed) {
  // One simulation, two input sources: sampled held state where it exists,
  // the bindings' accumulated nudges where it does not.
  final input = canHold
      ? ShipInput(thrust: keyboard.snapshot.isHeld(KeyPosition.w))
      : controls.takeAccumulated();
  game.advance(elapsed, input);
}
```

Two details make this robust rather than merely present. First, **every
sampled control needs a fallback binding or a capability gate** — and the
framework checks: in debug builds, sampling a key on a press-only surface
with no binding covering it prints a *dead control* warning naming the key
and the fix, because a control that cannot possibly work should say so
instead of silently doing nothing. Second, keep the fallback's bindings
positional too (`KeyPosition.w`, not `KeyCode.w`) so both schemes stay
WASD-shaped on every layout.

## In the weeds

The details worth knowing when something surprises you — how terminals differ,
why a keypress sometimes reaches a text field instead of your binding, and the
focus machinery underneath it all.

### Terminal support & the keyboard protocol

Key releases, held state, and per-key positions come from the Kitty keyboard
protocol. Fleury asks every terminal for it automatically; there is no flag to
set and nothing to opt into. A terminal that only partly supports it is
negotiated back down *before your app sees a keystroke*, so asking can never
cost the user their ability to type.

One carve-out: inside a terminal multiplexer — tmux, screen — the automatic ask
stops at the safe tier, because a query answered through the multiplexer says
nothing reliable about the host terminal. Set
`FLEURY_KEYBOARD=lifecycle` to override this when you know your setup passes the
protocol through, or `FLEURY_KEYBOARD=legacy` to opt out entirely on a terminal
where the query misbehaves.

The practical upshot for app code is the single reactive read you already saw —
`Keyboard.of(context).capabilities.supportsHeldState` — plus its siblings
(`supportsPositions`, `distinguishesRepeats`). Branch on the capability, never
on a terminal name.

### Typed text is not a key event

Printable input arrives as text, not as a `KeyEvent` — the text widgets claim it.
That is why `q` can quit your app while a focused text field keeps typing `q`:
the field claims the character first, and only unclaimed text falls through to
your bindings. You get this for free; it is worth knowing when a shortcut
"stops working" inside an input.

### Focus & traversal

Keys go to the focused part of the tree, so focus is what decides *where*. Most
widgets manage it themselves; when you need to drive it directly:

```dart
final _node = FocusNode(debugLabel: 'editor');
_node.requestFocus();
final hasIt = _node.hasFocus;
_node.dispose();
```

To react when focus enters or leaves a whole subtree — pause a simulation, dim a
panel, stop a cursor blinking — wrap it in `FocusDetector`:

```dart
FocusDetector(
  onFocusChange: (hasFocus) => setState(() => _active = hasFocus),
  child: Focus(focusNode: _node, child: body),
);
```

Inside a `FleuryApp(home: ...)` route or an explicit `FocusTraversalGroup`,
`Tab` / `Shift+Tab` move between focusable nodes. A bare widget passed directly
to `runApp` has the focus manager but no traversal policy; wrap it in a group
when it has multiple controls.

**One key to watch:** inside `FleuryApp(home: ...)` (or another explicit
`Navigator`), `Esc` already pops the current route by default. If you also bind
it, be deliberate about which should win; to intercept the pop rather than race
it, reach for a `PopScope` (see
[Navigation](/fleury/guides/navigation/#guarding-back)).
