Wrap a control in `FormField` to validate its value. Put related fields inside
`Form` to validate and submit them together. Values stay in your application
state; the form handles inline errors and focus.

## Validate a form

focus moves to **Name**. Enter a name and a lowercase slug, then press **Enter**
in Slug or choose Create again.

A validator returns an error message, or `null` when the value is valid.
Validation starts when you submit or call `validate()`. Once feedback has been
shown, editing or updating a value refreshes it automatically. It does not move
focus as you correct errors.

`FormField` discovers the ordinary control inside it and supplies its invalid
styling and error semantics. A `SizedBox` or `Padding` around that control is
fine. Give every input a visible label and a matching `semanticLabel`.

`FormController.submit()` validates every mounted, enabled field before running
`onSubmit`. Invalid submission focuses the first error and scrolls it into view
when it is inside a `ScrollView`. Repeated submissions share the same pending
attempt.

Create controllers once in `State` and dispose them with that state, as the
complete source shows. You can omit the form controller when all actions live
inside the form: `Form.of(context)` gets its controller and rebuilds readers
when its state changes.

## Save and retry

Choose a **Simulated server response**, then **Save**:

- **Success** shows progress, then confirms which value was saved.
- **Name taken** puts an error on Name. Edit the name to clear it, choose Success,
  and retry.
- **Offline** keeps the draft and offers a retry. Change the response to Success
  and save the same draft.

The service is local to this example; no request is sent.

Handle expected service failures inside `onSubmit` so the button, Enter, and
semantic submission all get the same feedback. Keep field errors in application
state and pass them to `FormField.error`. Clear the error when the user edits
that value. A failure affecting the whole request belongs in the form's status
message instead of on an unrelated field.

Take a snapshot of the values before the asynchronous operation. After it
finishes, check `mounted` before updating the UI. Put success-only actions, such
as closing a dialog, in the successful branch of that callback.

`submit()` returns `false` when validation rejects an attempt or the callback
leaves a field with an error, including a server error passed to `FormField.error`.
It applies pending UI updates before checking, so setting an error inside
`onSubmit` is enough. Unhandled save exceptions propagate to an awaiting caller.
The example displays its offline failure inside `save()` and handles that expected
exception in the shared button/Enter handler; it never reports a failed save as
successful.

Use `isBusy` to disable Submit and back actions for the whole attempt. Use
`isSubmitting` to lock field editing after validation: `readOnly: true` keeps
text fields focusable; `onChanged: null` disables choice controls. Keep fields
enabled during validation, because disabled fields are skipped. For a navigation
guard, use `PopScope(canPop: !form.isBusy)`.

## Validate related fields

A validator can read another application-owned value. Enter different made-up
passwords, then choose **Check**. Errors appear and keyboard focus stays on
Check. Choose **Confirm** instead to move focus to the first invalid field.
After checking, changing either password refreshes the comparison.

`validate(autofocus: false)` displays errors without moving focus or scrolling.
The default is `true`; it applies to that validation call, not the control's
initial focus. If concurrent calls share a validation pass, any request for
autofocus enables it. Submit always requests autofocus.

Validators are synchronous and should only read state and return an error.
`validate()` returns a future so it can wait for pending widget updates before
checking those values. For a server check, use the save-and-retry pattern above.

`clearErrors()` hides validator feedback without changing values. Controlled
`FormField.error` messages stay until your application clears them. To reset a
form, reset your values and controlled errors, then clear validator feedback.

Attach `field.focusNode` to the control that should receive focus when the value
is invalid. Call `field.valueChanged()` after updating the value, and forward
`field.error` to your custom error semantics or styling. The field supplies the
visible error message below the composite by default.

The ordinary `FormField(child: ...)` constructor expects one value control.
Use separate fields for separate values, or the builder for a composite; wrapping
two unrelated controls in one ordinary field is an error.
