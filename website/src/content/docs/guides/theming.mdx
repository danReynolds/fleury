Fleury separates what a color means from where it is painted. Put app-wide
colors and styles in `ThemeData`, then use a widget's `style` property for a
local exception. Ordinary styling stays as small as `style: CellStyle(...)`;
state-specific styling is available when you need it.

| You need to… | Use |
|---|---|
| Theme the whole app | `FleuryApp(theme: …)` |
| Theme one subtree | `Theme(data: …, child: …)` |
| Style one widget | `style: CellStyle(…)` |
| Change focus, selection, or validation styling | `CellStyle.state(…)` |

## Create a theme

Start with semantic roles: a primary accent, focus, status colors, and the
terminal's base surfaces. Widgets consume those roles consistently, so changing
one theme value updates screens, dialogs, and controls together:

<CodeDemoSplit file="amber_theme.dart">
<Fragment slot="code">
```dart
const amber = ThemeData(
  brightness: Brightness.dark,
  colorScheme: ColorScheme(
    background: RgbColor(0x1C, 0x18, 0x14),
    foreground: RgbColor(0xEB, 0xDB, 0xB2),
    surface: RgbColor(0x2A, 0x24, 0x1E),
    primary: RgbColor(0xE8, 0xA3, 0x3D),
    focus: RgbColor(0xF2, 0xC5, 0x5C),
    success: RgbColor(0x8E, 0xC0, 0x7C),
    warning: RgbColor(0xE8, 0xA3, 0x3D),
    error: RgbColor(0xE5, 0x6B, 0x5B),
    info: RgbColor(0x83, 0xA5, 0x98),
  ),
  mutedStyle: CellStyle(dim: true),
  selectionStyle: CellStyle(inverse: true),
  focusedStyle: CellStyle(bold: true),
  borderStyle: BorderStyle.rounded,
);

FleuryApp(theme: amber, home: const Dashboard());
```
</Fragment>

`ThemeData.dark()` and `ThemeData.light()` provide useful starting points.
Use `copyWith(...)` when only a few roles differ:

```dart
final theme = ThemeData.dark().copyWith(
  colorScheme: ColorScheme.fromSeed(Colors.violet),
  borderStyle: BorderStyle.double,
);
```

Pass the result to `FleuryApp`. If no theme is supplied, Fleury uses its built-in
defaults, so `Theme.of(context)` always returns a value.

## Style one widget

Every first-party control keeps the common case direct:

```dart
TextInput(
  controller: query,
  style: const CellStyle(foreground: Colors.cyan),
)
```

That style becomes the control's base appearance. It does not erase the
framework's focus, disabled, or validation cues; those still layer on when the
state changes. The same `CellStyle` works on `Text`, `Button`, `Checkbox`,
`Select`, and the rest of the control set.

### CellStyle

A `CellStyle` describes terminal paint: foreground and background colors plus
attributes such as bold, dim, italic, underline, inverse, and strikethrough.
`inverse: true` conceptually swaps the effective foreground and background
colors, including terminal-default colors when either is unset. The terminal
renderer emits the standard SGR reverse-video attribute; the browser renderer
reproduces the same exchange.

```dart
const CellStyle(
  foreground: RgbColor(0x3D, 0xDC, 0x97),
  bold: true,
  underline: true,
)
```

Styles merge field by field. An unset value inherits; explicitly setting a
boolean attribute to `false` turns that inherited attribute off.

## Style control states

Use `CellStyle.state` only when an interactive widget should look different as
its state changes. Put it on `ThemeData.interactiveStyle` to set the app-wide
policy, or pass it to one widget's ordinary `style` property for a local
exception:

<CodeDemoSplit file="control_states.dart" layout="demo-wide">
<Fragment slot="code">
```dart
const theme = ThemeData(
  interactiveStyle: CellStyle.state(
    focused: CellStyle(inverse: true, bold: true),
    hovered: CellStyle(underline: true),
    selected: CellStyle(foreground: Colors.green, bold: true),
    invalid: CellStyle(foreground: Colors.red, underline: true),
    disabled: CellStyle(dim: true),
  ),
);

FleuryApp(theme: theme, home: const DeploymentForm());
```
</Fragment>

In the demo, Tab or click between controls, hover in the browser, toggle
**Approved**, and submit the empty field. The same theme value handles focus,
hover, selection, validation, and the disabled button.

The available states are deliberately small:

| State | Used by |
|---|---|
| `hovered` | Pointer-aware controls while the pointer is over them |
| `focused` | Focusable controls |
| `selected` | Chosen values such as checkboxes, radio options, selected ranges, dates, and swatches |
| `disabled` | Controls that cannot be changed or activated |
| `invalid` | Form-aware value controls with a validation error |

A widget emits only states that make sense. A `Button`, for example, can be
focused or disabled but is never selected or invalid.

### Local state changes

The same `style` property accepts either kind of value:

```dart
// One base style; inherited state cues remain.
Button(
  label: 'Deploy',
  style: const CellStyle(foreground: Colors.cyan),
  onPressed: deploy,
)

// Only this button changes its focused treatment.
Button(
  label: 'Deploy',
  style: const CellStyle.state(
    focused: CellStyle(inverse: true, underline: true),
  ),
  onPressed: deploy,
)
```

Use `CellStyle.none` for a state when a widget should deliberately suppress an
inherited cue. It means “apply no paint for this state”; semantics are
unchanged:

```dart
FormField(
  validator: () => query.text.isEmpty ? 'Enter a query.' : null,
  child: TextInput(
    controller: query,
    style: const CellStyle.state(invalid: CellStyle.none),
  ),
)
```

When the field reports an error, its validation message still renders and
assistive tooling still receives it; only that input's invalid chrome is
neutral.

## Theme roles

### ColorScheme

`ColorScheme` names colors by meaning rather than hue:

| Role | Used for |
|---|---|
| `foreground` / `background` | Default text and app fill |
| `surface` | Opaque raised fills such as dialogs and popups |
| `primary` | Main accent and active affordances |
| `focus` | Focused panes and controls |
| `success` `warning` `error` `info` | Status |

```dart
final colors = Theme.of(context).colorScheme;

Text('Deployed', style: CellStyle(foreground: colors.success));
```

Colors may be `RgbColor(r, g, b)`, `AnsiColor(index)`, `IndexedColor(index)`,
or a named `Colors.*` value. Nullable foreground, background, and surface roles
may be left unset to preserve the user's terminal colors. Set `surface` when a
dialog or popup must fully cover content behind it.

### Text and structural roles

`ThemeData` also supplies shared roles for non-control content:

| Role | Purpose |
|---|---|
| `textStyle` | Default text inherited by the app |
| `mutedStyle` | Secondary copy, hints, and separators |
| `selectionStyle` | Selected rows and items |
| `focusedStyle` | General focus emphasis |
| `errorStyle` | Validation messages and default invalid cue |
| `borderStyle` | Default box-drawing shape |

Use the picker to preview each role as a local `style:` across the same
organized set of text and controls. This demonstrates that every stylable
surface shares the `CellStyle` vocabulary; in normal application code, use each
semantic role for the purpose named in the table. The surrounding panel uses
`borderStyle`, which changes box-drawing glyphs rather than cell paint:

<FleuryExample id="themes.roles" cols={56} rows={14} interactive />

`interactiveStyle` is the shared interactive-state policy. `errorStyle`
remains the semantic text style for messages; the `invalid` entry in the
`CellStyle.state(...)` assigned to `interactiveStyle` lets widget chrome differ
from message text.

## Light and dark values

Choose the mode when you construct the app theme. `ThemeData.dark()` and
`ThemeData.light()` set `brightness` for you, or pass it explicitly to
`ThemeData(...)`:

```dart
FleuryApp(theme: ThemeData.dark(), home: const Dashboard());
```

Fleury does not guess the terminal's background. When another value needs a
light and dark variant, read the choice through the ambient theme:

```dart
final shadow = context.theme.adaptive(
  light: const AnsiColor(8),
  dark: const AnsiColor(0),
);
```

For code outside a widget build method, use
`theme.brightness.pick(light: ..., dark: ...)`.

## Theme scope and precedence

Wrap a subtree in `Theme` for a local palette, such as a branded panel or a
high-contrast preview. The nearest theme wins:

```dart
Theme(
  data: Theme.of(context).copyWith(
    colorScheme: ColorScheme.fromSeed(Colors.amber),
  ),
  child: const InspectorPane(),
)
```

Control styling resolves from broadest to narrowest:

1. The widget's built-in defaults.
2. `ThemeData.interactiveStyle`.
3. The widget's `style` property.

Base styles merge through all three layers. For a state, the nearest non-null
state entry replaces the broader entry for that state. Multiple active states
then layer in this order: selected, hovered, focused, invalid. Disabled is
exclusive, keeping unavailable controls visually stable.

Most applications only need the first two levels. Local state entries are an
escape hatch for an exceptional control, not required wiring.

Theme authors can also customize independently painted parts—such as a switch
track, progress track, or syntax token—through `FleuryWidgetTheme` in
`ThemeData.extensions`. Ordinary application themes do not need that extension.
