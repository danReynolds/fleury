A terminal UI can become the user's workspace or help them finish one step in a
command. Fleury supports both: **full-screen** uses the terminal viewport;
**inline** reserves a smaller region beneath the current cursor.

The examples below run a real Fleury form inside illustrated terminal buffers.
In the full-screen tab, run the command to watch the form take over. Finish or
cancel to return to the shell; **Run again** resets the browser illustration.

## Choose for the workflow

| | Full-screen | Inline |
|---|---|---|
| Good fit | Editors, dashboards, file managers, multi-pane workspaces | Pickers, setup forms, confirmations, bounded progress displays |
| Space | The terminal's width and height | Full width and an explicit number of rows, clamped to the terminal height |
| Earlier shell output | Hidden while the app runs; restored on exit | Remains in the main buffer; reserving space can move it into scrollback |
| When Fleury exits | Leaves the alternate screen | Clears the live region |
| Lasting result | Print after awaiting `runApp` | Print after awaiting `runApp` |

Choose full-screen when users need room to explore, navigate between views, or
keep several things in view. Choose inline when the UI is one step in a shell
workflow and the surrounding output provides useful context. Duration alone
doesn't decide it: a compact status display can run for a long time.

For ordinary command output, a report, or a single text prompt, plain CLI output
may be enough. If your design needs a growing transcript above a live prompt,
Fleury's current inline mode does not yet support that arrangement.

## What the terminal does

Most modern terminal emulators provide a **main screen buffer**, where your shell
and command output live, and an **alternate screen buffer** for interactive apps.
Entering the alternate screen hides the main screen; leaving it reveals the
previous contents. This is the mechanism behind Fleury's default full-screen
mode. It fills the terminal viewport, not the desktop display.

Inline stays in the main buffer. Fleury asks the terminal for the cursor's
position, reserves rows there, and confines painting and clearing to that region.
It translates mouse and text-caret positions into the widget tree's coordinates.
The widgets receive a smaller viewport and use the same layout and input APIs.

<TerminalBuffers />

Screen placement is separate from input handling. **Both modes use raw input**
so Fleury can react to individual keys, manage focus, and edit text. The shell
waits while the app runs. Mouse reporting is optional in both modes; enabling it
affects native terminal selection throughout the window. Terminal-specific
selection modifiers and scrollback behavior still apply.

The alternate screen normally has no scrollback of its own. A `ScrollView` or
`ListView` scrolls content inside your UI, independently of terminal scrollback.
Redrawing frames does not create a durable history of the interaction, and
Fleury's inline mode clears its final frame on exit.

## Choose the mode at startup

Pass your widget tree to `runApp` and choose its terminal mode:

```dart
await runApp(
  app,
  mode: const TerminalMode.inline(rows: 17, mouse: true),
  enableHotReload: false,
);
```

Here, `app` is your root widget. For full-screen, use
`mode: const TerminalMode(mouse: true)` with the same tree. The inline constructor
requires a row count; the full-screen constructor has no height setting. Mouse
input is optional in both.

Native inline currently requires macOS/Linux, terminal input/output, and cursor
position reporting. It does not support Windows or redirected input/output.
[Current inline support](#current-inline-support) describes the remaining limits.

Choose the mode for each `runApp` invocation. On native macOS/Linux terminals,
you can await one UI, run ordinary CLI code, and open another UI in the same
process. Each invocation gets a fresh driver and can choose its own mode.

Keep steps inside one session when they belong to a continuous UI, as the setup
form does. End the session when the CLI should regain control. Use handoff when
another program temporarily needs the terminal and you want to return to the
current UI with its state intact.

Setting `TerminalMode(alternateScreen: false)` alone does not create an inline
region: it provides neither the allocation nor the rendering bounds.

### Finish back at the prompt

When the setup form finishes, its host calls `requestExit()`. Fleury clears the
inline region or leaves the alternate screen, restores terminal input, and completes
`runApp`. The command can then print its result. That is why the summary in the
demo stays at the prompt after the form disappears.

The [native setup host](https://github.com/danReynolds/fleury/blob/main/packages/samples/bin/inline.dart)
shows this boundary. Treat a signal exit separately from a completed or cancelled
form: preserve its exit status and skip the ordinary result message. An unhandled
Ctrl+C returns `AppExit.signal(AppSignal.interrupt)`, conventionally exit code 130.
The sample disables hot reload so its startup and final
output run once; both terminal modes support development sessions.

### Give inline steps enough room

The setup form requests 17 rows for editing and 21 for review. Its native host
connects page changes to the terminal; the shared form only reports which step
is active:

```dart
ScopeBuilder<TerminalSession>(
  builder: (_, session) => InlineSetup(
    onComplete: (_) => requestExit(),
    onStepChanged: (step) async {
      if (session.isInline) await session.resizeInline(step.rows);
    },
  ),
)
```

`InlineSetup` is the [sample form](https://github.com/danReynolds/fleury/blob/main/packages/samples/lib/src/inline_setup.dart),
not a framework widget. In full-screen mode it simply uses the available space.

Read the session while building, then resize from an interaction or lifecycle
callback. Resizing erases the old allocation, reserves the new one, and repaints.
Requests during a subprocess handoff or suspension take effect on return.
Full-screen and remote sessions reject inline resize requests.

Use `Expanded` and scrollable content so a short terminal can still reach every
control. Keep primary actions visible while longer content scrolls. The setup
showcase stacks its preview at narrow widths. [Layout](/fleury/guides/layout/) and
[Lists & scrolling](/fleury/guides/lists-and-scrolling/) cover those widgets.

## Go from UI to CLI and back

Use an inline UI for one step in a longer command, return control to ordinary
CLI code, then open another UI. This native demo creates two configurations in
one process: **setup → text prompt → fresh setup → shell**.

<InlineRecording recording="inline-repeat" label="Watch UI → CLI → UI in one command" duration="20 seconds" />

After the first form closes, its summary stays in the terminal. The **Open setup
again?** prompt reads `y` with ordinary `stdin.readLineSync()`. The second form
starts with fresh widget state; completing it and answering `n` ends the command.
Each summary remains available in the terminal's scrollback.

Try the same flow from a Fleury checkout:

```sh
dart run packages/samples/bin/samples.dart inline --repeat
```

This recording runs the real native app; the shell context around it is a
recording fixture. No project files are written. Add `--full-screen` to try
successive alternate-screen sessions instead. Each `runApp` can choose its own
mode, so a command can also combine inline and full-screen steps.

The loop belongs in the command's host. Await `runApp` before printing, reading
input, or opening the next UI:

```dart
Future<void> repeatSetup() async {
  while (true) {
    InlineSetupResult? result;
    final outcome = await runApp(
      FleuryApp(
        title: 'Project setup',
        home: InlineSetup(
          onComplete: (value) {
            result = value;
            requestExit();
          },
        ),
      ),
      mode: const TerminalMode.inline(rows: 21, mouse: true),
      enableHotReload: false,
    );

    if (outcome.signal case final signal?) {
      exitCode = switch (signal) {
        AppSignal.interrupt => 130,
        AppSignal.terminate => 143,
        AppSignal.hangup => 129,
      };
      return;
    }
    if (result == null) return;

    stdout.writeln(result!.summary);
    stdout.write('Open setup again? [y/N] ');
    await stdout.flush();
    if (stdin.readLineSync()?.trim().toLowerCase() != 'y') return;
  }
}
```

`InlineSetup` and `InlineSetupResult` are the sample's form and result type.
The [complete native host](https://github.com/danReynolds/fleury/blob/main/packages/samples/bin/inline.dart)
also adjusts the region height for each form step. A real command can do its
ordinary work between sessions—write the chosen configuration, run a build, or
print a report—then open the next UI when it needs interaction again.

Finishing a `runApp` disposes that UI. Keep any data needed by the next step in
the host. To lend the terminal to another program and return to the **same** UI
with its state intact, use [handoff](#let-another-program-use-the-terminal).

Await each invocation and let it create its default driver. Overlapping or
nested calls are rejected; an explicitly supplied native driver is used only
once. Handle signal outcomes before opening another UI: a hangup means the
terminal disconnected. If cleanup fails, Fleury reports an error and blocks new
sessions until ownership is safely returned.

Sequential native sessions require macOS/Linux TTY input. Windows and redirected
Dart stdin streams still permit one session per process. Another library must
not read input concurrently; cancelling a Dart stdin subscription can close its
descriptor, which Fleury cannot recover. Disable hot reload for a CLI with work
between sessions: hot restart reruns the entrypoint, including earlier prompts
and side effects.

## Output and subprocesses

By default, `runApp` captures stray output while it owns the terminal and replays
the retained output after exit. Calling `print` during the UI is not a way to
append permanent lines above it. Render live messages as widgets; print the
command's final result after awaiting `runApp`.

### Let another program use the terminal

Suppose the setup form offers **View in pager**. Selecting it opens the generated
configuration in `less`, a separate terminal pager. Pressing **q** closes it and
brings you back to the same form, with your name, template, and review step preserved.

<InlineRecording recording="inline-handoff" label="Watch setup open less and resume" duration="Native terminal recording" />

This is a recording of the real native app launching `less`, not a browser
simulation. Try it yourself from a Fleury checkout:

```sh
dart run packages/samples/bin/samples.dart inline --handoff
```

Choose **Review →**, then **View in pager**. The preview uses a temporary file
and removes it when the pager closes; no project files are created. Add
`--full-screen` to try the same handoff from the alternate screen.

`runWithHandoff` makes this work by temporarily giving the child control of the
terminal. Fleury pauses its painting and output capture, restores normal input,
and releases its screen. Without the handoff, the two programs would compete
for input and the child's output could disappear into Fleury's captured logs.
When the child exits, Fleury reclaims the terminal and redraws the existing UI.

```dart
await session.runWithHandoff(() async {
  final pager = await Process.start(
    'less', ['--', previewFile.path],
    mode: ProcessStartMode.inheritStdio,
  );
  await pager.exitCode;
});
```

The native host reads `session` from `ScopeBuilder<TerminalSession>` and creates
`previewFile` before the handoff. The form itself needs no process or terminal
code. This also works for an editor or an interactive Git command. In inline
mode, child output can remain above the resumed UI; full-screen mode re-enters
the alternate screen. On POSIX terminals, Ctrl+Z uses the same release-and-resume
lifecycle.

## Current inline support

Inline requires native macOS or Linux with terminal input/output and cursor
position reporting. Entry fails after restoring modes if Fleury cannot obtain
a valid cursor report. Windows inline mode and piped input/output are unsupported.

Natural content height, permanent log insertion above a running region, and
retaining the final frame are not implemented. Native image protocols fall back
to glyph rendering. Terminal emulators differ in how they reflow old lines on
resize; if cleanup cannot establish which rows it owns, it leaves uncertain
rows alone to protect earlier output.

Browser embeds take their size from the containing element. A served native
preview also has a host-controlled viewport; neither demonstrates a native
inline allocation. See [Serving and embedding](/fleury/architecture/serving-and-embedding/).
